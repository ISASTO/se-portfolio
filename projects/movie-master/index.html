01 / Problem

A business with no software—and no ordinary brand.

Movie Master began with a real person selling personalized movie recommendations. The service had customers, strong opinions, and a completely singular voice, but almost no technical infrastructure.

I set out to make the business legible and usable online without sanding off everything that made it memorable. That created a product problem more interesting than a conventional student brief: the site needed to be credible enough to transact through, but a generic polished landing page would have made the underlying idea less compelling.

The working constraints

  • An extremely small infrastructure budget.
  • A nontechnical collaborator and requirements that changed through conversation.
  • Real customers on both desktop and mobile.
  • A visual identity that needed to feel earnest, unusual, and unmistakably specific.
  • New functionality that could not make the basic storefront fragile.
02 / Decisions

Let complexity arrive only when a feature earns it.

The first version did not need an application framework or a database. It needed to load quickly, explain the offer, and work reliably. I kept the core static and added stateful services at the edge.

01

Preserve the voice

The visual system uses loud display type, testimonials, and deliberately heightened sales language. Usability became cleaner while the product’s strange personality stayed intact.

02

Keep the core static

GitHub Pages serves the storefront and game with almost no operational surface area. Static assets remain available even if analytics or leaderboard requests fail.

03

Add state at the boundary

A Cloudflare Worker and D1 database handle the features that truly require shared state: anonymous visitor counts, run telemetry, player profiles, and leaderboards.

04

Protect the primary experience

Observability is useful but noncritical. Telemetry calls are isolated so a failed analytics request cannot interrupt gameplay or prevent a visitor from using the site.

03 / Game

A hidden extra became its own engineering system.

What began as a small browser diversion grew into a real-time game with distinct modes, persistent records, controller support, instrumentation, and shared leaderboards.

The game runs a continuous update/render loop and manages moving entities, collision detection, projectiles, power-ups, escalating difficulty, pausing, and local statistics. Standard and Hardcore modes share most of the system while applying different failure rules.

Input became one of the best examples of finishing the last ten percent. Keyboard, pointer, and gamepad behavior need different handling. Controller input applies dead zones to avoid drift; if the active controller disconnects, the game pauses instead of silently leaving the player unable to respond.

Public leaderboards without accounts

I wanted a returning player to keep a name and improve one personal best without building a complete authentication product. A browser-held anonymous identity links the local player to validated daily and all-time records. The Worker normalizes names and scores before anything becomes public, while the UI can show the leaders and the player’s immediate neighborhood in the ranking.

The game taught me that “supports controllers” is a first draft. Disconnects, dead zones, focus loss, menu navigation, and recovery are the feature.
04 / Evolution

Requirements emerged from use.

There was no frozen rubric. Each layer came from an observed need: a clearer offer, a mobile layout problem, a desire to know whether people were visiting, a competitive game, then the reliability and moderation work that public scores require.

  1. Static business site Established the offer, voice, calls to action, and automatic GitHub Pages deployment.
  2. Responsive product polish Reworked navigation, testimonials, purchase paths, and mobile behavior around real content.
  3. Browser game Added a live game loop, multiple control schemes, modes, progression, and persistent local records.
  4. Anonymous analytics Introduced a Worker and D1 when shared visitor and run data finally justified server-side state.
  5. Public competition Added named daily/all-time boards, validation, score neighborhoods, migrations, and backend tests.
05 / Outcome

A tiny product that behaves like a real one.

Movie Master is live, supports real paid transactions, records real usage, and has continued to evolve without abandoning its original lightweight core.

More importantly, it changed how I think about engineering judgment. The most impressive architecture is not the one with the most pieces. It is the one whose pieces correspond to real requirements—and whose failures are contained so the product’s main purpose still works.

LESSON 01

Personality is a product requirement

A technically cleaner interface can still be wrong if it erases the reason people remember it.

LESSON 02

State belongs where it is needed

A static core can support a surprisingly capable product when stateful services are added deliberately.

LESSON 03

Noncritical systems should fail quietly

Analytics is valuable. It is never valuable enough to break the experience it is measuring.

LESSON 04

Real use changes the backlog

Actual players exposed edge cases and priorities that an isolated specification never would have produced.
