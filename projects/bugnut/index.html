01 / Problem

The site was not the repetitive part. Publishing was.

I make hand-drawn comics frequently. A normal gallery would leave me resizing pages, renaming files, creating thumbnails, counting pages, editing metadata, identifying spreads, and checking the result by hand.

That workflow has two bad properties: it steals time from the work the site exists to share, and it invites small inconsistencies every time content is added. The real software problem became: how much can the computer safely infer from an ordinary folder of exported artwork?

The answer shaped the entire project. Rather than build a content management interface, I built a small convention-driven publishing system around the way I already produce files.

02 / Workflow

One command replaces a fragile checklist.

The guided importer asks only for information the files cannot supply: source folder, title, content type, date, and a few optional editorial choices.

Manual workflow
  1. Sort and rename pages
  2. Rotate and resize images
  3. Remove metadata
  4. Create a cover thumbnail
  5. Count pages and spreads
  6. Edit the site catalog
  7. Check every route
  8. Publish
Bugnut workflow
  1. Drop exports in a folder
  2. Run npm run add-comic
  3. Confirm detected order
  4. Answer short prompts
  5. Preview and push

What the importer handles

  • Naturally sorts input filenames and asks the user to confirm reading order.
  • Copies rather than mutates source artwork, then normalizes output to sequential JPEG files.
  • Auto-rotates, flattens, strips metadata, and limits dimensions with Sharp.
  • Generates the gallery thumbnail and derives page counts from the directory.
  • Detects landscape pages that should occupy a two-page spread.
  • Updates a generated catalog, sorts sections by date, and runs content checks.

03 / Architecture

The directory is the source of truth.

Each comic is a folder of sequential page images plus a small comic.json containing only information that cannot be derived reliably.

Page count should not exist in two places. Neither should thumbnail state or spread detection. Duplicated metadata drifts; derived metadata can be rebuilt. The preparation script validates the folders and produces the catalog consumed by the Next.js application.

  1. Artwork folder Source exports
  2. Node pipeline Normalize + derive
  3. Next.js app Reader + galleries
  4. GitHub Pages Static delivery

Convention over configuration

Predictable names such as 001.jpg, 002.jpg, and a constrained metadata schema make the rest of the system simpler. The importer generates those conventions, so their reliability does not depend on remembering a document every time I publish.

04 / Reliability

Broken content should fail before deployment.

The pipeline checks slugs, dates, content types, page sequences, missing files, and type-specific rules. A one-page work cannot silently contain a stack of pages; a comic cannot skip from 003.jpg to 005.jpg; invalid metadata should stop the build with an actionable message.

The production test command runs the complete Next.js build and then tests the rendered HTML. Every push to the main branch repeats content preparation during the build before GitHub Actions publishes the static output. Local convenience and deployment correctness therefore rely on the same pipeline.

INPUT

Validate at the boundary

The importer rejects bad paths, impossible dates, duplicate slugs, and invalid content shapes early.

TRANSFORM

Use a temporary directory

Images are prepared away from the final path, then moved into place only after processing succeeds.

BUILD

Regenerate deterministically

The catalog and thumbnails can be rebuilt from the source folders instead of repaired by hand.

DELIVERY

Test the deployed shape

Rendered-output tests catch failures that type checking alone cannot see in a static export.

05 / Outcome

Publishing no longer requires editing the application.

A new comic can move from an export folder to the live site through a guided command, a preview, and a push. The public reader stays fast because the final product is statically generated.

Building for my own repeated workflow created unusually direct feedback: every unnecessary prompt, unclear error, or manual correction appeared again on the next release. That pressure made the internal tool—not only the visible website—a first-class product.

LESSON 01

Automate the repeated judgment

The largest payoff came from removing a workflow I actually perform, not automating for its own sake.

LESSON 02

Derive instead of duplicate

Page counts, thumbnails, and spreads are more reliable when computed from canonical source files.

LESSON 03

Error messages are interface design

A command-line tool still needs to explain what failed, what remains safe, and what the user should do next.

LESSON 04

Internal tools shape the product

A pleasant publishing path makes the public site more current, consistent, and sustainable.
